# local-opt 実装状況と実行結果

`local-opt.md` で定義した Wasm 関数単位ローカル割り当て（allocation-only MaxSAT）の、現時点での実装状況とベンチマーク結果。

最終更新: 2026-07-07

---

## サマリー

| 項目 | 状態 |
|------|------|
| CLI (`--opt-locals`) | あり |
| 前処理（web 分解・干渉・コピー検出） | 一部実装 |
| MaxSAT 定式化（H1–H5, S1–S2, B1） | 実装済み |
| 解の適用（index 付け替え・自己コピー削除） | メモリ上のみ |
| Wasm バイナリ出力・Δbytes 測定 | 未実装 |
| 実験プロトコル（§8） | 未着手 |

現段階は **プロトタイプ**。ローカルスロット数の削減までは動くが、設計書の主目的であるバイト数最小化の評価や、大規模コーパスでの実験には至っていない。

## 実装状況（local-opt.md 対応）

### 問題設定（§1）

- allocation-only（命令順・種類は変えず index 付け替えと自己コピー削除のみ）という方針は踏襲している。
- **目的関数はバイト数ではなく命令数ベースの近似**（コピー削除重み = 節約命令数、ローカルスロット削減重み = 1）。§5 のバイト数目的とは未整合。
- §1 の「タイムアウト時は恒等割り当てにフォールバック」は **未実装**。タイムアウトした関数は変更なしでスキップされる。

### 前処理（§2）

| 項目 | 状態 | 備考 |
|------|------|------|
| §2.1 Web 分解 | 実装済み | reaching-def + union-find による def-use グループ化。LocalGraph 相当の意図はあるが Binaryen との完全一致は未検証。 |
| §2.2 Liveness / 干渉 | 一部 | def/use のプログラム点区間の重なりで干渉を判定。**value numbering による精密化は未実装**（保守的に干渉が多く出る可能性あり）。 |
| §2.3 コピー対 | 実装済み | `local.get` + `local.set` / `local.tee` の連続パターン。利得は命令数（2 / 1）で、Wasm バイト数ではない。 |
| §2.4 ループ重み | 未実装 | サイズ目的のみ想定のため対象外。 |

### 定式化（§3–§6）

| H4 干渉 | 実装済み |

| S2 ローカル宣言コスト | 実装済み（ε = 1 のタイブレーカ） |

### ソルバー

- 設計書想定の RC2 等ではなく **Z3 Optimize** を使用。
- 関数ごとタイムアウト: デフォルト **30 秒**（`--locals-timeout-ms` で変更可）。
- 並列実行: `-j` で関数単位並列化に対応。

## 実行結果

### 実行コマンド

```bash
cargo run --release -- --opt-locals benchmarks/rosetta/addition_chains_initial.wasm -j20
```

### モジュール全体

| 指標 | 結果 |
|------|------|
| 処理関数数 | 13 |
| 改善 | 4 |
| スキップ | 5（no locals × 2、タイムアウト × 3） |
| 命令数 | 1990（±0） |
| ローカルスロット | 144（**−9**） |
| 削除コピー数 | 0 |
| ソルバー合計時間 | ~101 s |

このコーパスでは **ローカルスロット統合のみが効き、コピー削除による命令削減は発生しなかった**。命令数は変わらず、ローカル宣言の圧縮効果もまだバイト数としては未計測。

### 関数別

| 7 | 3 | 10 | 13 | ~130 | unchanged | ±0 | 0.01s |
| 8 | 5 | 26 | 33 | ~858 | **improved** | −1 | 0.02s |

（H4 節数 = 干渉辺数 × web 数。R = N の見積もり。）

### 観察

1. **BB 数だけではソルバー難易度は予測できない。** func 16（12 BB）は 2.6 s で解けるが、func 13（14 BB）はタイムアウト。ボトルネックは web 数と干渉辺数。
2. **現設定（Z3, 30 s）の実用限界はおおよそ web 30 台 + 干渉 150 超。** func 9（32 webs, 108 干渉）はギリギリ解ける。func 13/15 はこの境界を超える。
3. **func 14 は桁違いに重い**（95 webs, 1951 干渉, ~18 万 H4 節）。連結成分分解なしでは現実的でない。
4. **タイムアウト率 3/13（≈23%）** で、改善できたのは 4/13（≈31%）。ただしコーパスは 1 ファイルのみで、wasm-opt 後ベースラインでもない。
5. 改善はすべてローカルスロット削減。コピー削除（S1）が効いたケースはこの実行ではゼロ。

## 設計書との主なギャップ（優先度順）

1. **バイト数目的（§5）と Δbytes 測定（§8）** — 現状は命令数近似のみ。Wasm 書き戻しとバイト数計測がないと設計書の評価軸に乗れない。
2. **干渉の value numbering 精密化（§2.2）** — 未実装のため干渉が過大になり、ソルバーが重くなる・ coalescing 機会を逃す両方のリスクがある。
3. **タイムアウト時の恒等割り当てフォールバック（§1）** — 現状はスキップ（無変更）なので設計上の保証と一致。
4. **連結成分分解（§9）** — 大きい関数（func 14 等）への対応に必須。
5. **S3 ULEB ペナルティ / B2 対称性破壊** — web 数 128 未満の関数が大多数なら S3 は低優先。B2 はソルバー性能次第。
6. **実験プロトコル全体（§8）** — wasm-opt ベースライン、コーパス層化、正しさ検証、相乗効果対照は未着手。
