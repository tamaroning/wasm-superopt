# Wasm 関数単位ローカル割り当ての MaxSAT 定式化(allocation-only)

wasm-opt の `coalesce-locals` / `merge-locals` / `reorder-locals` が貪欲ヒューリスティックで解いている「値 → ローカル index の割り当て」問題を、関数単位で厳密に(MaxSAT で)解き、wasm-opt 最適化済みバイナリに対する上積みを測るための問題設定と定式化。ブロック内の命令スケジュール(どの値をどこで計算するか、スタックの使い方)は**変更しない**。変更するのは各値がどのローカル index に格納されるかのみであり、その帰結として自己コピーになった `local.set`/`local.get` 対を削除する。

---

## 1. 問題設定

**入力**: wasm-opt の最適化パイプライン(例: `-O3` または `-Oz`)を通した後の Wasm 関数 F。パラメータ数 p、ローカル(パラメータ含む)集合 L、各ローカルの型 τ: L → {i32, i64, f32, f64, ...}。

**出力**: 新しいローカル割り当て、すなわち後述の web 集合 W から新 index 集合 {0, ..., R−1} への写像 α と、それに伴い削除可能になった命令の集合。

**保存すべき意味論**: Wasm のローカルは関数プライベートであり、外部観測されるのは (a) メモリ・グローバル・テーブルへのアクセス列、(b) 関数の返り値、(c) トラップの有無、のみ。allocation-only 変換では命令の順序も種類も変えず index の付け替えと自己コピー削除しか行わないため、以下のハード制約(§4)を満たす任意の割り当てが意味論を保存する。特に、境界での値の受け渡しに修正コード(shuffle)を挿入する必要は一切ない。各 web は生存期間全体で単一の index を占有するからである。この「新規コードを一切生まない」ことが、フル最適化(CEGAR 型)との違いであり、実装と正しさ検証を大幅に単純化する。

**目的**: 出力バイナリのバイト数最小化(wasm-opt との比較を実測バイト数で行うため。スループット目的への変更は §5 末尾)。

**実行可能性の保証**: 恒等割り当て(元の index をそのまま使う)は常にハード制約を満たすので、問題は常に SAT。ソルバーがタイムアウトした場合は恒等割り当てにフォールバックすれば、ベースラインより悪化することはない。

---

## 2. 前処理: 関数から抽出する構造

### 2.1 Web 分解

同一ローカル index を共有していても、データフロー上つながっていない def-use の塊は独立に割り当ててよい。Binaryen の `LocalGraph`(各 `local.get` に到達しうる `local.set` の集合を計算する)を使い、次の関係の推移閉包で def と use をグループ化する:

- `local.get` g と、g に到達しうる各 `local.set` s は同じグループ
- 同じ `local.get` に到達しうる 2 つの `local.set` は同じグループ(φ に相当)

得られる各同値類を **web** と呼ぶ。W = {w₁, ..., w_N}。パラメータ i の初期値(暗黙の def)も 1 つの def として扱い、それを含む web を「パラメータ web」と呼ぶ。use を 1 つも持たない def のみの web は任意の空き index に置けるので、そのまま変数に含めてよい(あるいは前処理で除去)。

同一ローカル由来の複数 web を異なる index に割り当てることは **live range splitting** に相当し、coalesce-locals が扱えないケース(merge-locals の `TODO` になっている部分的 live range 重なり)を自然に包含する。異なるローカル由来の web を同一 index に割り当てることが **coalescing** である。

### 2.2 Liveness と干渉

Binaryen の `LivenessWalker` 相当で基本ブロックごとの live-in/live-out を web 単位で計算する。web u, v の干渉を次で定義する:

> **interfere(u, v)** ⟺ あるプログラム点で u と v が同時に live であり、かつその点で両者が同じ値を保持すると証明できない。

後半の条件は Binaryen の `calculateInterferences` が行っている value numbering による精密化と同じで、これを入れないとコピー由来の重なり(`local.set x (local.get y)` の直後など)がすべて干渉扱いになり、coalescing の機会が消える。実装上は各基本ブロック内で local な value numbering を行い、「同値と証明できた重なり」だけを干渉から除外する。保守的側(証明できなければ干渉)に倒せば正しさは保たれる。

### 2.3 コピー対と削除利得

コピー命令とは web u の値を web v の index へ写す命令、すなわち

- `local.set x (local.get y)` 型(2 命令: get + set)
- `local.tee x (local.get y)` 型(tee の結果がさらに使われる場合)

の各出現である。コピー対集合 C ⊆ W × W × ℕ を、(u, v, c) の形で列挙する。c はその出現を削除できたときに節約されるバイト数:

```
c = bytes(local.get y) + bytes(local.set x)   # set 型。通常 2 + 2 = 4 バイト
c = bytes(local.get y)                        # tee 型は tee → 内側の get に置換されるだけの場合など、
                                              # 実際の書き換え後エンコードから計算する
```

opcode 1 バイト + ULEB index(index < 128 なら 1 バイト)。**利得は必ず「割り当て確定後に実際に行う書き換え」から逆算して定義する**こと。ここが曖昧だと目的関数値と実測 Δbytes がずれ、評価が壊れる。

削除条件: コピー出現 (u, v, c) は α(u) = α(v) のとき自己コピーとなり削除できる。ただし削除後もスタック効果が同じであることを書き換え規則として明示する必要がある(§7)。

### 2.4 ループ重み(スループット目的の場合のみ)

各コピー出現にループ深度 d を記録しておく。サイズ目的では使わない。

## 3. 決定変数

index の上限 R は R = N(web 数)で十分(恒等割り当てが常に可能なため実際には元のローカル数でもよいが、splitting を許すなら N)。

| 変数 | 範囲 | 意味 |
|---|---|---|
| a_{w,r} | w ∈ W, r ∈ {0..R−1} | web w が index r に割り当てられる |
| m_{u,v} | (u,v,·) ∈ C | web u と v が同一 index(コピー削除可能) |
| used_r | r ∈ {0..R−1} | index r に少なくとも 1 つの web がある |

型ごとに index 空間を分割する実装(型 t の web は型 t 用の index 区間のみ)にすると a 変数が減り、型制約(§4)が不要になる。以下では分割しない一般形で書く。

---

## 4. ハード制約

**(H1) Exactly-one**: 各 w ∈ W について Σ_r a_{w,r} = 1。基数制約の標準符号化(sequential counter / cardinality network)で CNF 化。

**(H2) パラメータ固定**: パラメータ i のパラメータ web w について a_{w,i} = 1。Wasm ではパラメータの index は呼び出し規約で固定。非パラメータ web はパラメータ index に割り当ててもよい(そのパラメータ web と干渉しなければ)。これは coalesce-locals もやっている合法な最適化。

**(H3) 型整合**: τ(u) ≠ τ(v) なる u, v と各 r について ¬a_{u,r} ∨ ¬a_{v,r}。(index 空間を型で分割すれば不要。)

**(H4) 干渉**: interfere(u, v) なる各対と各 r について ¬a_{u,r} ∨ ¬a_{v,r}。

**(H5) 補助変数の定義**:

```
m_{u,v} → ∨_r (a_{u,r} ∧ a_{v,r})     # 実際は m_{u,v,r} ← a_{u,r} ∧ a_{v,r} を導入し
m_{u,v} ↔ ∨_r m_{u,v,r}              # Tseitin 変換で
a_{w,r} → used_r                      # used の片方向で十分(ソフト節が ¬used を好むため)
```

m は「削除利得を主張する側」にしか使われないので、片方向含意(m → 同一 index)だけで正しい。逆方向は最適解では自動的に成立する。

---

## 5. ソフト制約(目的関数)

最小化するバイト数を、ソフト節の重みとして符号化する。

**(S1) コピー削除**: 各コピー出現 (u, v, c) について soft 節 (m_{u,v}, weight = c)。同一 web 対に複数のコピー出現があれば重みを合算して 1 節にしてよい。

**(S2) ローカル宣言コスト**: soft 節 (¬used_r, weight = ε)。Wasm のローカル宣言は (count, type) の連長圧縮なので、ローカル 1 個の削減が常に 1 バイト減るわけではない。ε はコピー削除より十分小さいタイブレーカ(例: コピー重みを 100 倍スケールし ε = 1)として設定し、厳密なバイト数は書き換え後の実測に委ねる。

**(S3) ULEB ペナルティ(大きい関数のみ)**: index r ≥ 128 の `local.get`/`local.set`/`local.tee` は index が 2 バイトになる。web w の静的使用回数を n_w として、r ≥ 128 の各 (w, r) に soft 節 (¬a_{w,r}, weight = n_w × 100)。web 数(正確には型分割後の各区間の web 数)が 128 未満の関数では S3 は不要で、これが大多数。

**目的関数の全体**:

```
minimize  Σ_{(u,v,c)∈C, m=0} c  +  Σ_r used_r · ε  +  Σ_{r≥128} n_w · [a_{w,r}] · β
```

これは wasm-opt 側の対応物と正確に比較できる。coalesce-locals の「removedCopies 最大化、同点で maxIndex 最小化」という辞書式ヒューリスティックの、真の同時最適化版になっている。

**スループット目的への変更**: S1 の重みを c × k^d(d = ループ深度、k ≈ 10)に置き換えるだけ。coalesce-locals がバックエッジのコピーを重く扱っているのと同型だが、こちらは厳密に最適化される。ただし評価指標が実測バイト数でなくなるため、比較には実行ベンチマークが必要になる。最初の実験ではサイズ目的を推奨。

---

## 6. 対称性破壊

パラメータでない index はすべて互換(index < 128 の範囲では ULEB 長も同一)なので、割り当ての置換対称性が N! 級で存在する。以下を**ハード制約**として加える。恒等でない任意の解は置換で正規形に移せるため、最適値は失われない:

**(B1)** used_r → used_{r−1}(r > p、すなわち非パラメータ区間で index は詰めて使う)

**(B2)** 各非パラメータ index 区間で、web に固定の全順序(例: 最初の def のプログラム点順)を入れ、「index r に入る最小 web は index r−1 に入る最小 web より大きい」という辞書式順序制約。B1 だけでもかなり効くので、B2 は性能を見て追加。

S3(ULEB ペナルティ)を使う場合、B2 の固定順序と頻度順が衝突しないよう、順序を「使用回数降順、同点でプログラム点順」に取る。

---

## 7. 解の適用(書き換え)

最適割り当て α を得たら:

1. すべての `local.get i` / `local.set i` / `local.tee i` の index を、その出現が属する web w の α(w) に置換する。同一 index の異なる web は異なる新 index になりうる(splitting)。
2. 自己コピーの削除:
   - `(local.set x (local.get x))` → 削除(スタック効果: 何も残さない → 一致)
   - `(local.tee x (local.get x))` → `(local.get x)` に置換
   - drop に包まれている等の変種は、前処理でコピー対として数えた出現と 1 対 1 対応する規則のみ適用する(数えていないパターンを消すと目的関数値と実測がずれる)
3. ローカル宣言部を再構成(型ごとに連長圧縮)。
4. `wasm-validate` で検証。ここで重要なのは、**この段階で他の最適化パスを一切走らせない**こと。走らせるとベースラインにも同じパスを適用しなければ公平でなくなり、測っているものが「割り当ての上積み」でなくなる。

非自明な注意点として、tee の削除で式木の形が変わる場合は Binaryen IR 上で書き換えてから再放出するのが安全。バイナリを直接パッチするより、Binaryen のカスタムパスとして実装し `--no-validation` なしで通すのが現実的。

## 8. 実験プロトコル(wasm-opt 比の測定)

1. **コーパス**: 実アプリの .wasm(WasmBench 等の既存コーパス、あるいは Circom / Rust / C++ 由来の混成)。SuperStack 論文の知見から、コンパイラの成熟度で余地が大きく変わるため、由来別に層化しておく。
2. **ベースライン**: `wasm-opt -Oz`(サイズ目的なので)を収束するまで(または 2 回)適用したバイナリ B。関数ごとのバイト数を記録。
3. **提案手法**: B の各関数に §2–7 を適用。ソルバーは RC2 等の MaxSAT ソルバー、関数ごとにタイムアウト(例: 10–60 s)。タイムアウト時は anytime 解(RC2 は途中解を出せる)か恒等割り当てにフォールバック。
4. **公平性のための対照**: 提案手法適用後にもう一度 `wasm-opt -Oz` を通した場合の縮み(相乗効果)と、B にもう一度 `-Oz` を通した場合の縮み(固定点確認)を別列で報告する。主指標はあくまで「追加パスなしの Δbytes」。
5. **指標**: 関数ごとの Δbytes、改善関数の割合、削除コピー数、ローカル数削減、ソルバー時間、タイムアウト率、web 数・干渉辺数と時間の相関(スケーラビリティ曲線)。
6. **正しさ**: wasm-validate に加え、リファレンスインタプリタまたは V8 で差分テスト(同一入力で実行し観測出力一致)。allocation-only なので理論上は H1–H5 の正しさに帰着するが、web 分解と liveness のバグはここで捕まえる。
7. **解釈**: 上積みが出た関数について、それが (a) 部分的 live range 重なり(merge-locals の TODO ケース)、(b) coalesce-locals の 2 順序探索の失敗、(c) splitting による新規機会、のどれに由来するかを分類すると、フル最適化(CEGAR 型)に進む価値の判断材料になる。

## 9. スコープ制限と落とし穴

- **non-defaultable なローカル**(GC / reference types の non-nullable 参照)は構造的支配の制約(`local-structural-dominance`)があり、任意の web 統合が index の再利用条件を壊しうる。第一段の実験では該当関数を除外するのが安全。
- **例外処理(EH)**: try-catch の pop を含む関数は liveness が複雑になる。除外またはブロック境界を保守的に扱う。
- **liveness の保守性**: unreachable コードや br_table の扱いを Binaryen の LivenessWalker に合わせておかないと、Binaryen より強い干渉を仮定して機会を失う(正しさは保たれるが上積みが過小評価される)。
- **測定の罠**: gzip / Brotli 後のサイズは index の再配置で非単調に変わりうる(Binaryen 側にも gzip 未対応の TODO がある)。raw バイト数を主指標、圧縮後サイズを副指標として両方報告する。
- **問題サイズ**: 干渉制約は最悪 O(N²·R) 節。web 数が数百を超える関数では、干渉グラフの連結成分ごとに独立の MaxSAT に分解できる(成分間は index 空間を共有するが、used_r の合成だけ後処理で調整すればよい)。それでも大きい場合はその関数をスキップし、スキップ率を報告する。

## 10. この定式化が包含するもの・しないもの

包含する: coalesce-locals(統合 + コピー削除 + index 数最小化)、merge-locals(value numbering 込みの干渉定義と splitting により、部分的重なりケースも含めて一般化)、reorder-locals の index 割り当て側面(S2, S3, B1)。

包含しない: simplify-locals が行う sink / tee 化(命令スケジュールの変更)、ブロック内の命令列合成(SuperStack のフル探索)、rematerialization、制御構造の戻り値化。これらは次段の CEGAR 型フル最適化の領域であり、本実験で上積みが観測された関数群がその投資判断の根拠になる。
